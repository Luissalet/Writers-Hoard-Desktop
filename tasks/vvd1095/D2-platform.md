# D2-platform: VVD platform/editor surfaces vs Writer (offline desktop)

Method: read all 3,705 string keys of `D2-platform.txt` (data only), clustered them into capabilities, then opened Writer code to confirm each OFFLINE capability (R = repo "Writers hoard desktop"). Behaviour beyond what a label says is marked "(inferred)". Paths are relative to R. Prior matrix `tasks/worldcraft1041-feature-inventory.md` was read for overlap but not trusted as proof; every PRESENT/PARTIAL below was confirmed in code. Status tokens: PRESENT, PARTIAL, ABSENT, UNKNOWN, n/a (ONLINE).

Online-by-nature groups, summarised (rows marked n/a): accounts/login/public nav, membership/roles/invites, billing/plan limits, studio/payouts, wikiChrome.dashboard.* (analytics, earn, shop, inbox, followers, perks, setup cards, notifications, ~266 keys), wikiChrome.community.* (posts, polls, replies, moderation, bans, members-only gating, ~315 keys), subdomain/custom domain/DNS/SSL, audience (password/invite) hosting, subscribe-by-email, public theme sharing, Workshop marketplace (likes, storefront, engagement analytics, GitHub deploy, contributors, request-a-tool), cloud content moderation, stock public gallery, browser-extension "add from web" account sync.

## Top offline gaps worth implementing

Ranking weighs user value for a worldbuilding/writing desktop app, how much VVD promotes the feature, and cost. Rule for all items: additive only. Do not change existing record shapes, MCP tool names or schemas; add optional fields, new tools and new files, keep CAS/Undo patterns, and extend JSON/ZIP/clone portability in the same change.

1. **Whole-world Markdown vault export (and optional media toggle).** Size M. VVD sells "every document as readable Markdown + JSON + optional media" and Obsidian's selling point is plain files. Writer only has JSON/ZIP backup plus HTML/PDF world bible and wiki. Sketch: new `src/services/worldMarkdownExport/` that walks the same engine `exportProject` strategies used by `src/services/zipBackup.ts`, converts rich text with the existing `htmlToMarkdown` (`src/engines/writings/manuscriptExport.ts`, `src/services/aiBridge/markdown.ts`), emits one `.md` per card/chapter/note with YAML frontmatter (type, fields, aliases, tags, eraId) and `[[wikilinks]]` resolved from `services/codexReference/indexedMentions.ts`, tables as CSV, timelines as Markdown lists, media under `media/`; UI in Dashboard backup section and EditProjectModal with include-media checkbox, size estimate, phase text and cancel (AbortController); MCP `wh_world_markdown_export` (read-only, returns base64 zip or writes via native save). Round-trip is already covered by the Obsidian importer. Risk: memory on large projects (stream per engine, JSZip streaming), must not touch `createProjectZipArchive` output.

2. **Standalone documents as wiki pages + bulk curation.** Size L. Risks: edition snapshot hashing and CAS revisions, era effective-document resolution, validators that currently reject unknown kinds (old app versions reading new profiles).
